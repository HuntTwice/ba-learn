## 5. Coach 引导与学生回答

### 引导一：递归不是“组件自己无限调用自己”

递归需要终止条件。菜单节点有 `children` 时，它是分支：渲染目录，并把 `children` 交给下一层 `MenuTree`；没有可见子节点时，它是叶子：渲染可点击菜单项，不再递归。数据每深入一层都会变小，因此最终一定到达叶子。

### 引导二：路由状态与交互状态不是一回事

当前高亮项应由 `route` 推导，因为地址栏、浏览器前进后退和刷新都可能改变页面；只记录最后点击项会与真实页面失去同步。展开集合则包含用户主动打开的目录，属于界面状态，但当前页面的祖先目录也应自动展开，保证高亮项可见。

### 引导三：本节对应的 BuildAdmin 源码

- `menuVertical.vue` 创建最外层 `el-menu`，向它传入当前激活标识、是否折叠及只展开一个目录等配置。
- `menuTree.vue` 遍历当前层节点：有子节点时渲染 `el-sub-menu` 并递归调用自身；否则渲染 `el-menu-item`。
- BuildAdmin 使用统一的 `getMenuKey()` 生成菜单标识，避免各层使用不同规则。
- 当前练习只实现单套垂直菜单，不复制横向、双栏、国际化和远程链接等产品复杂度。

### TypeScript 类型表达追问

学生原问题：

> `type ViewComponent = NonNullable<(typeof viewComponents)[string]>` 我不理解这个什么意思，已经超出了我所学的 ts 语法了，解释一下吧。

Coach 反馈：判断合理。该表达式组合了类型位置的 `typeof`、索引访问类型和 `NonNullable` 工具类型，不应要求初学者机械照抄。课堂将其从内到外拆解，同时允许本节使用更直白的 `type ViewComponent = () => Promise<unknown>`；高级推导写法作为“让类型跟随变量自动变化”的阅读知识，不列为本节必须掌握内容。

Coach 完整讲解：

这段同时使用了三个尚未系统学习的 TypeScript 知识：

```ts
type ViewComponent =
  NonNullable<(typeof viewComponents)[string]>
```

先看运行时变量：

```ts
const viewComponents = import.meta.glob('/src/views/**/*.vue')
```

它的值大致类似：

```ts
{
  '/src/views/home/HomeView.vue': () => import('...'),
  '/src/views/user/UserDetailView.vue': () => import('...'),
}
```

因此它的类型大致可以理解为：

```ts
Record<string, () => Promise<unknown>>
```

也就是一张“字符串路径映射到异步加载函数”的表。

第一层，`typeof viewComponents`：这里的 `typeof` 出现在类型位置，不是运行时得到字符串 `"object"` 的那个用法。它表示“请 TypeScript 取得变量 `viewComponents` 的完整类型”，结果大致为：

```ts
Record<string, () => Promise<unknown>>
```

第二层，`(typeof viewComponents)[string]`：这是索引访问类型，表示“如果用一个字符串 key 从这张映射表取值，取得的值是什么类型”。例如：

```ts
viewComponents['/src/views/home/HomeView.vue']
```

取出的值大致是：

```ts
() => Promise<unknown>
```

第三层，`NonNullable<T>`：这是 TypeScript 自带的工具类型，它会从类型中排除 `null` 和 `undefined`。例如：

```ts
type A = string | undefined | null
type B = NonNullable<A>
```

最终 `B` 是 `string`。

所以完整表达式的阅读顺序是：

```text
typeof viewComponents
→ 得到整张组件映射表的类型

(typeof viewComponents)[string]
→ 得到映射表中一个值的类型

NonNullable<...>
→ 排除这个值不存在的情况
```

最终得到的类型大致是：

```ts
() => Promise<unknown>
```

本节不要求学生掌握该高级推导写法，可以直接使用更直观的版本：

```ts
type ViewComponent = () => Promise<unknown>
```

其中：

- `()` 表示它是一个函数。
- `Promise` 表示调用后异步返回结果。
- `unknown` 表示当前不具体规定加载结果的内部结构。

两种写法的区别：

```ts
type ViewComponent = () => Promise<unknown>
```

是由开发者手工描述类型，简单直观。

```ts
type ViewComponent =
  NonNullable<(typeof viewComponents)[string]>
```

### `String(route.name ?? '')` 语法追问

学生原问题：

> `String(route.name ?? '')` 这是什么意思？

Coach 完整讲解：

这段表达式分为从内到外两个步骤：

```ts
route.name ?? ''
```

`??` 是空值合并运算符。它表示：如果左侧不是 `null` 或 `undefined`，使用左侧；如果左侧是 `null` 或 `undefined`，使用右侧的默认值。

```ts
const value = route.name ?? ''
```

等价于：

```ts
let value

if (route.name === null || route.name === undefined) {
  value = ''
} else {
  value = route.name
}
```

示例：

```ts
'user-detail' ?? '' // 'user-detail'
undefined ?? ''     // ''
null ?? ''          // ''
```

`??` 与 `||` 不完全相同。`||` 会把空字符串、数字 0 和 false 也当作需要回退的假值；`??` 只处理 `null` 与 `undefined`：

```ts
0 || 10  // 10
0 ?? 10  // 0
```

在当前场景中，我们只想处理“路由名不存在”，所以 `??` 的含义更准确。

外层：

```ts
String(...)
```

会把括号中的值转换成字符串。Vue Router 的 `route.name` 不只可能是 string，也可能是 Symbol、null 或 undefined；Element Plus 菜单的 active index 需要与 `el-menu-item` 的字符串 index 比较，因此这里统一转换成字符串。

完整运行示例：

```ts
route.name = 'user-detail'

route.name ?? ''
// 得到 'user-detail'

String('user-detail')
// 得到 'user-detail'
```

没有路由名时：

```ts
route.name = undefined

route.name ?? ''
// 得到 ''

String('')
// 得到 ''
```

为什么不直接写 `String(route.name)`：

```ts
String(undefined) // 'undefined'
String(null)      // 'null'
```

这里得到的不是空值，而是真正的文字字符串 `"undefined"` 或 `"null"`。虽然当前菜单中通常没有这个 index，不一定立刻出现视觉错误，但它错误地表达了“没有激活项”。使用 `String(route.name ?? '')` 后，没有路由名就明确得到空字符串。

所以整句可以翻译为：

> 如果当前路由有名字，就把名字转换成字符串；如果没有名字，就使用空字符串，表示当前没有对应的激活菜单。

### 祖先路径搜索思路检查

学生原回答：

> 如果让我从 adminMenuRules 中寻找 user-detail，因为他是递归遍历的，所以可以用一个外层变量，存储他的遍历路径。

Coach 完整反馈：

核心方向正确：递归搜索时需要保存“当前从根节点走到这里经过了哪些目录”。这份路径就是找到目标后要交给菜单展开状态的祖先数组。

但共享的外层可变数组存在回退问题。假设菜单有两个并列目录：

```text
系统管理
├── 角色管理
└── 用户管理
    └── 用户详情
```

如果搜索“角色管理”失败后，没有把已经 push 的节点正确 pop 掉，再去搜索“用户管理”时，旧分支可能残留在路径中。外层数组方案可以实现，但必须严格维护“进入时 push、离开失败分支时 pop”的回溯过程。

本节采用更容易推理的递归参数方案：

```ts
function findAncestorNames(
  nodes: AdminMenuRule[],
  targetName: string,
  ancestors: string[] = [],
): string[] | undefined {
  for (const node of nodes) {
    if (node.name === targetName) {
      return ancestors
    }

    const result = findAncestorNames(
      node.children ?? [],
      targetName,
      [...ancestors, node.name],
    )

    if (result) {
      return result
    }
  }

  return undefined
}
```

`ancestors` 表示到达当前层之前已经经过的节点。`[...ancestors, node.name]` 创建新数组，不修改上一层的数组，因此搜索一个分支失败后，不需要手动 pop，也不会污染兄弟分支。

寻找 `user-detail` 的过程：

```text
第一层检查 system-management
→ 进入 children，ancestors = ['system-management']

第二层检查 user-management
→ 进入 children，ancestors = ['system-management', 'user-management']

第三层找到 user-detail
→ 返回当前 ancestors
→ ['system-management', 'user-management']
```

返回值不包含 `user-detail` 自己，因为 `default-openeds` 只需要目录的 index；叶子本身由 `default-active` 负责高亮。

### 核心验收一：为什么只创建一个 `el-menu`

Coach 问题：

> 为什么 `AdminMenuTree` 里面不能每递归一层就创建一个新的 `<el-menu>`，而应该只在 `AdminAside` 中创建一个 `<el-menu>`？

学生原回答：

> 不清楚

Coach 完整讲解：

`el-menu` 不是普通的视觉包装标签，而是整棵菜单的状态容器。它统一管理：

- 当前激活项 `default-active`。
- 哪些 `el-sub-menu` 展开或收起。
- 整体是否折叠 `collapse`。
- 菜单项与子菜单之间的父子注册关系。
- 菜单级配置和样式。

正确结构只有一个菜单根：

```text
AdminAside
└── el-menu（统一状态容器）
    └── AdminMenuTree（只生成结构）
        ├── el-menu-item：首页
        └── el-sub-menu：系统管理
            └── AdminMenuTree
                └── el-sub-menu：用户管理
                    └── AdminMenuTree
                        └── el-menu-item：用户详情
```

虽然 `AdminMenuTree` 递归创建了多个组件实例，但它们生成的 `el-sub-menu` 和 `el-menu-item` 最终都属于同一个最外层 `el-menu`。因此一个 `default-active="user-detail"` 就能在整棵树中找到用户详情，一个 `collapse` 就能统一折叠整棵菜单。

如果每层递归都创建 `el-menu`：

```text
el-menu A
└── el-sub-menu：系统管理
    └── el-menu B
        └── el-sub-menu：用户管理
            └── el-menu C
                └── el-menu-item：用户详情
```

那么 A、B、C 是三个独立菜单实例，不再是一棵由同一容器管理的菜单树。外层 A 接收到的 `default-active`、`collapse` 和展开状态不会自然统一管理内层 B、C；各层可能分别维护激活项、展开项、边框和折叠行为，父子注册关系也被新的菜单根截断。

职责划分是：

```text
AdminAside / el-menu
→ 管理整棵菜单的状态

AdminMenuTree
→ 根据数据递归生成目录和叶子结构
```

类比来说，一所学校只有一个总管理系统，年级和班级是其中的层级；不能每进入一个班级就重新创建一所独立学校，否则统一的学生状态和管理规则会被切断。

Coach 追问：如果每层递归都创建一个 `el-menu`，最核心的问题是什么？

学生原回答：

> 无法统一管理菜单状态。

Coach 反馈：正确。多个 `el-menu` 会形成多个独立状态容器，外层无法统一管理整棵树的激活、展开和折叠。学生已掌握 `el-menu` 状态容器与 `AdminMenuTree` 结构生成器的职责边界，本项通过。

### 核心验收二：菜单递归与路由递归

Coach 问题：

> `AdminMenuTree.vue` 和 `dynamic.ts` 都要递归遍历同一份 `adminMenuRules`，但它们递归的目的有什么不同？提示：一个最终产生界面，一个最终产生路由记录。

学生原回答：

> 一个最终产生界面。一个最终产生路由记录。

Coach 反馈：方向正确，但回答基本复述了提示。完整区别是：`AdminMenuTree` 消费树形数据，生成用户可见的目录和叶子组件；`dynamic.ts` 消费同一棵树，找到可导航页面叶子并调用 `router.addRoute()`，建立 URL、路由名称和页面组件的匹配关系。需要通过“只递归其中一条链路会发生什么”继续确认理解。

Coach 追问：如果 `AdminMenuTree` 已递归、侧栏能看到“用户详情”，但 `dynamic.ts` 仍只遍历最外层，点击用户详情会发生什么？为什么？

学生原回答：

> 只看到用户详情菜单，点击后不跳转到对应的视图。

Coach 反馈：核心判断正确。更准确地说，点击处理器仍可能调用 `router.push()` 并改变地址，但深层 `user-detail` 路由没有注册，Vue Router 无法将该 URL 映射到用户详情组件；当前项目会由兜底路由渲染 404。菜单显示链路与路由匹配链路缺一不可，本项通过。

### 核心验收三：菜单状态的事实来源

Coach 问题：

> 为什么 `activeMenu` 适合直接根据当前 route 计算，而 `sidebarCollapsed` 适合保存在 Pinia？请从“谁是事实来源”和“哪些组件需要使用”两个角度回答。

学生原回答：

> 因为高亮菜单的数据来源是 url，而折叠是提供给组件共享的。

Coach 反馈：正确。当前 URL 经 Vue Router 解析得到 route，route 是页面位置的事实来源，`activeMenu` 只是派生界面表现；若再把激活项独立存入 Pinia，会形成两份可能不同步的数据。侧栏折叠则是用户界面配置，需要 Aside、折叠按钮和布局尺寸等多个组件共同消费，因此适合保存在 Pinia。本项通过。
