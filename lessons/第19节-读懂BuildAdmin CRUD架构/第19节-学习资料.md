# 第 19 节：读懂 BuildAdmin CRUD 架构——学习资料

## 1. 学习目标

学完本资料后，你应当能够：

1. 说清 BuildAdmin 一套 CRUD 页面由哪些部分协作完成。
2. 从一次界面操作出发，沿事件、控制器、API、响应数据追踪到页面更新。
3. 区分列表数据、筛选数据、表单数据和加载状态。
4. 理解配置驱动 CRUD 的收益与代价，不把 `baTable` 当成“会自动完成一切的黑盒”。

## 2. 前置知识

### 2.1 CRUD 是四类业务动作

CRUD 是 Create、Read、Update、Delete 的缩写，分别对应新增、读取、更新和删除。后台管理中的一个用户管理模块，往往不只包含四个按钮，还包含分页、搜索、排序、表单校验、加载提示、选择行、错误恢复等配套状态。

典型接口可以是：

```text
GET    /admin/user.User/index   获取列表
GET    /admin/user.User/edit    获取待编辑行的完整数据
POST   /admin/user.User/add     新增
POST   /admin/user.User/edit    更新
DELETE /admin/user.User/del     删除
```

这里第二个 `edit` 是读取编辑数据，第四个 `edit` 是提交更新。它们路径相同但 HTTP 方法不同，因此含义不同。

### 2.2 状态不等于服务器数据

一个 CRUD 页面至少有四组状态：

- `table.data`：当前显示的行。
- `table.filter`：页码、每页数量、排序和搜索条件。
- `form.items`：弹窗中正在编辑的数据副本。
- `loading`、`operate`、`selection`：界面正在做什么。

例如 `table.loading = true` 不是业务数据，而是在告诉界面“列表请求尚未结束”；`form.operate = 'Edit'` 不是用户字段，而是在控制弹窗以编辑模式显示。

### 2.3 `provide/inject` 是祖先向后代共享依赖

业务页面创建一个 `baTable` 实例：

```ts
const baTable = new baTableClass(api, tableConfig, formConfig)
provide('baTable', baTable)
```

后代组件获取同一个对象：

```ts
const baTable = inject('baTable') as baTableClass
```

这不是复制一份数据。表格组件、表头组件和弹窗表单拿到的是同一个响应式控制器，所以任何一处修改 `baTable.table.data` 或 `baTable.form.operate`，其他使用者都能看到变化。

## 3. 核心概念

### 3.1 五个角色各司其职

BuildAdmin 用户 CRUD 主线可以拆成五个角色：

| 角色 | 代表文件 | 职责 |
| --- | --- | --- |
| 业务页面 | `views/backend/user/user/index.vue` | 选择 API 地址，声明业务列和默认表单值，组装页面 |
| 通用控制器 | `utils/baTable.ts` | 保存响应式状态，编排加载、翻页、编辑、提交、删除和刷新 |
| API 适配器 | `api/common.ts` 中的 `baTableApi` | 把 index、add、edit、del 等动作转换为 HTTP 请求 |
| 展示组件 | `components/table/index.vue` 及 header | 根据状态渲染表格、分页和按钮，把用户事件交给控制器 |
| 业务表单 | `views/backend/user/user/popupForm.vue` | 声明用户字段、校验规则和用户模块特有交互 |

通俗地说：页面是组装者，API 是快递员，`baTable` 是调度员，通用组件是显示器和操作面板，弹窗表单是业务数据编辑器。

### 3.2 控制器为什么存在

如果每个管理页面都自己写加载、翻页、打开弹窗、提交、删除和刷新，会产生大量重复代码。`baTable` 把稳定的流程收拢起来，业务页面只提供变化的部分，例如接口前缀、列配置、默认值和特殊钩子。

它不是 Pinia store。`baTable` 通常由当前业务页面创建，生命周期跟随页面；Pinia 更适合用户身份、主题等跨页面共享的全局状态。

### 3.3 命令与状态形成闭环

一次 CRUD 操作通常经过下面的闭环：

```text
用户事件
  → 通用组件转成交互事件
  → baTable 修改控制状态并调用 API
  → API 返回业务数据
  → baTable 写回响应式状态
  → Vue 根据新状态重新渲染
```

只看接口文件会漏掉界面状态，只看 Vue 模板会漏掉请求编排。阅读源码时要沿闭环走一遍。

## 4. BuildAdmin 源码拆解

以下路径均位于 `F:/project/MyProject/buildadmin/web/src`。

### 4.1 组装入口：用户页面

`views/backend/user/user/index.vue` 创建：

```ts
const baTable = new baTableClass(
  new baTableApi('/admin/user.User/'),
  { column: [/* 用户列表列配置 */] },
  { defaultItems: { gender: 0, money: '0', score: '0', status: 'enable' } }
)

baTable.mount()
baTable.getData()
provide('baTable', baTable)
```

这几行分别完成：

1. 用接口前缀生成 API 对象。
2. 用列配置描述用户表格怎样显示和搜索。
3. 给新增表单准备默认值。
4. 初始化搜索相关状态并加载首屏列表。
5. 把同一实例提供给 Table、TableHeader 和 PopupForm。

模板本身很短：`TableHeader` 显示顶栏操作，`Table` 显示列表，`PopupForm` 显示新增或编辑表单。页面的业务差异主要进入配置和表单，而不是重复实现通用流程。

### 4.2 API 适配器：baTableApi

`api/common.ts` 的构造函数把控制器前缀展开为动作地址：

```ts
new baTableApi('/admin/user.User/')
```

大致得到：

```text
index    → /admin/user.User/index
add      → /admin/user.User/add
edit     → /admin/user.User/edit
del      → /admin/user.User/del
sortable → /admin/user.User/sortable
```

`index(filter)` 使用 GET，把分页、排序和搜索作为 `params`；`edit(params)` 使用 GET 获取完整编辑行；`del(ids)` 使用 DELETE；`postData(action, data)` 使用 POST 提交新增或编辑。

API 类只负责怎样发请求，不决定弹窗何时出现，也不直接给表格赋值。

### 4.3 首次加载列表

页面执行 `baTable.getData()` 后，`utils/baTable.ts` 的关键过程是：

```ts
this.table.loading = true
return this.api.index(this.table.filter)
  .then((res) => {
    this.table.data = res.data.list
    this.table.total = res.data.total
    this.table.remark = res.data.remark
  })
  .finally(() => {
    this.table.loading = false
  })
```

输入是 `table.filter`，处理端是 `api.index()` 和服务器，输出写入 `data/total/remark`。无论成功失败，`finally` 都关闭 loading。

`components/table/index.vue` 再把这些状态绑定给 Element Plus：

```vue
<el-table :data="baTable.table.data" v-loading="baTable.table.loading">
  <!-- 按 column 配置生成列 -->
</el-table>
<el-pagination :total="baTable.table.total" />
```

因此不是表格组件自己请求数据，而是控制器请求后改变状态，表格组件被动渲染。

### 4.4 翻页链路

用户改变页码时：

```text
el-pagination current-change
→ Table 的 onTableCurrentChange(page)
→ baTable.onTableAction('current-page-change', { page })
→ table.filter.page = page
→ onTableHeaderAction('refresh')
→ getData()
→ api.index(新的 filter)
→ data 与 total 更新
```

这里最关键的是“先改查询条件，再刷新”。如果只刷新而没有更新 `filter.page`，服务器仍会返回旧页。

### 4.5 新增链路

点击新增后，表头把事件交给 `onTableHeaderAction('add')`，控制器调用：

```ts
this.toggleForm('Add')
```

`toggleForm` 会深拷贝 `form.defaultItems` 到 `form.items`，再把 `form.operate` 设为 `Add`。`popupForm.vue` 通过下面的条件打开弹窗：

```vue
:model-value="['Add', 'Edit'].includes(baTable.form.operate!)"
```

提交时，表单先校验，再由 `baTable.onSubmit()` 把 `Add` 转成 `add`，调用 `api.postData('add', form.items)`。成功后刷新列表并关闭弹窗。

新增使用深拷贝，是为了避免用户修改表单时把 `defaultItems` 本身也改掉，导致下次打开新增表单带着上次残留值。

### 4.6 编辑链路

点击某行编辑后：

```text
行按钮 edit
→ onTableAction('edit', { row })
→ toggleForm('Edit', [row.id])
→ getEditData(row.id)
→ api.edit({ id })
→ form.items = res.data.row
→ PopupForm 根据 operate='Edit' 显示完整数据
```

列表行常常只包含展示所需字段，敏感字段或关联数据也可能需要服务器重新整理。因此 BuildAdmin 不是直接把列表行塞进表单，而是按主键请求编辑详情。

提交编辑与新增共用 `onSubmit()`；区别来自 `form.operate` 被转换为 `edit`，最终请求对应地址。

### 4.7 删除链路

单行删除把当前主键组成数组，批量删除从 `table.selection` 提取主键。二者最终都调用：

```ts
this.api.del(ids).then(() => {
  this.onTableHeaderAction('refresh', {})
})
```

删除成功后重新请求服务器数据，而不是仅在前端数组中移除行。这样列表、总数和服务器最终状态能重新对齐。确认框和权限按钮等交互可由表格按钮组件承担，本节只关注控制器主链。

### 4.8 表单为什么单独成组件

`popupForm.vue` 包含用户模块特有字段和规则，例如用户名、用户组、头像、手机号、性别及新增/编辑时不同的密码规则。这些内容无法仅靠通用表格控制器推断。

它通过 `inject('baTable')` 取得共享实例，将输入框绑定到 `baTable.form.items`，提交时调用 `baTable.onSubmit(formRef)`。因此表单负责“编辑什么、怎样校验”，控制器负责“何时请求、成功后怎样刷新和关闭”。

## 5. 完整示例与运行过程

下面是一个不依赖 BuildAdmin 其他组件的缩小版，用来展示同样的分层思想。

### 5.1 API 端

```ts
export interface User { id: number; name: string }

let rows: User[] = [{ id: 1, name: '小明' }]

export async function listUsers() {
  return { list: [...rows], total: rows.length }
}

export async function addUser(input: Omit<User, 'id'>) {
  rows.push({ id: Date.now(), ...input })
}
```

### 5.2 控制端

```ts
import { reactive } from 'vue'
import { addUser, listUsers } from './userApi'

export function createUserCrud() {
  const state = reactive({
    rows: [] as Array<{ id: number; name: string }>,
    total: 0,
    loading: false,
    dialogOpen: false,
    form: { name: '' },
  })

  async function load() {
    state.loading = true
    try {
      const result = await listUsers()
      state.rows = result.list
      state.total = result.total
    } finally {
      state.loading = false
    }
  }

  function openAdd() {
    state.form = { name: '' }
    state.dialogOpen = true
  }

  async function submit() {
    await addUser({ name: state.form.name })
    state.dialogOpen = false
    await load()
  }

  return { state, load, openAdd, submit }
}
```

### 5.3 页面端

```vue
<script setup lang="ts">
import { onMounted } from 'vue'
import { createUserCrud } from './userCrud'

const crud = createUserCrud()
onMounted(crud.load)
</script>

<template>
  <button @click="crud.openAdd">新增</button>
  <p v-if="crud.state.loading">加载中...</p>
  <ul><li v-for="row in crud.state.rows" :key="row.id">{{ row.name }}</li></ul>
  <div v-if="crud.state.dialogOpen">
    <input v-model="crud.state.form.name" />
    <button @click="crud.submit">保存</button>
  </div>
</template>
```

运行后，页面挂载调用 `load()`，列表出现“小明”。点击新增时只改变表单和弹窗状态；保存时 API 数据改变，随后再次 `load()`，新用户才进入列表。这就是 BuildAdmin `baTable` 主线的最小版本。

## 6. 常见错误

1. **把 `baTable` 当成表格组件。** 它是控制器类；真正渲染表格的是 `components/table/index.vue`。
2. **只找用户专属 API 文件。** 用户列表使用通用 `baTableApi`，接口前缀在业务页面传入。
3. **认为 `provide/inject` 会复制状态。** 后代拿到同一个实例，修改会互相可见。
4. **拿列表行直接当完整编辑数据。** 列表可能裁剪字段，BuildAdmin 会按 id 请求编辑详情。
5. **只修改数组，不重新同步服务器。** BuildAdmin 在提交和删除成功后刷新列表，让总数和当前页面重新对齐。
6. **混淆 `table.loading` 与 `form.loading`。** 前者对应列表加载，后者对应编辑详情加载。
7. **认为配置驱动等于没有业务代码。** 列、默认值、字段、校验和特殊跳转仍由业务模块负责。
8. **一开始就读完 `baTable.ts` 每个细节。** 应先按一条用户操作追调用链，再补读搜索、拖拽和钩子等支线。

## 7. 自测题

1. `index.vue`、`baTable.ts`、`baTableApi`、`Table.vue`、`popupForm.vue` 各负责什么？
2. 首次加载列表时，筛选条件从哪里进入请求，响应数据写到哪里？
3. 翻页为什么必须先更新 `table.filter.page`？
4. 新增弹窗为什么使用 `cloneDeep(defaultItems)`？
5. 编辑为什么先请求 `api.edit({ id })`，而不是直接使用列表行？
6. `PopupForm` 怎样得到页面创建的 `baTable` 实例？
7. 新增或编辑成功后，列表为什么要刷新？
8. `baTable` 和 Pinia store 的使用范围有什么差别？

## 8. 参考答案

1. 页面负责组装和业务配置；`baTable.ts` 负责状态与流程编排；API 类负责 HTTP 动作；Table 负责展示与上报交互；PopupForm 负责业务字段和校验。
2. `table.filter` 传给 `api.index()`；成功响应的 `list/total/remark` 分别写入 `table.data/total/remark`。
3. 刷新只会按照现有 filter 再请求；不先改 page，请求参数仍是旧页码。
4. 防止编辑 `form.items` 时连默认值对象一起被修改，保证每次新增都有干净默认值。
5. 列表数据可能不完整或不是最新状态；按 id 获取详情能让服务器提供适合编辑的完整数据。
6. 页面 `provide('baTable', baTable)`，表单 `inject('baTable')`，两者共享同一个实例。
7. 重新从服务器获得当前页和总数，使前端与服务器最终状态一致，也避免手工处理分页边界。
8. `baTable` 通常服务当前业务页面；Pinia store 适合跨页面、跨组件长期共享的应用状态。
