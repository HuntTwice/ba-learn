## 2. 为什么需要状态管理

Vue 组件可以用 `ref()` 和 `reactive()` 保存状态。如果一份数据只属于一个组件，这已经足够：

```vue
<script setup lang="ts">
import { ref } from 'vue'

const dialogVisible = ref(false)
</script>
```

问题出现在多处需要同一份数据时。例如后台系统中的昵称：

- 顶部栏显示昵称；
- 个人资料页允许修改昵称；
- 欢迎页也显示昵称。

如果每个组件各写一份 `ref('小明')`，它们是三个互不关联的变量。个人资料页修改自己的变量，顶部栏不会知道。可以通过逐层 props 和 emits 传递，但当组件相隔很远时，传递链会变长，而且中间组件可能根本不关心这份数据。

Pinia 提供一个独立于具体组件的响应式仓库。多个组件调用同一个 store 时，获得的是同一份状态。任何一处更新，其他正在使用它的组件都会响应式刷新。

## 3. 状态应该放在哪里

状态管理的第一能力不是会写 `defineStore()`，而是会判断状态归属。

### 3.1 组件局部状态

只被单个组件使用，并且组件销毁后无需保留：

- 某输入框是否聚焦；
- 一个弹窗内部当前走到第几步；
- 当前按钮是否处于悬停状态。

这类状态保留在组件的 `ref()` 或 `reactive()` 中更直接。

### 3.2 提升到共同父组件的状态

只有少数相邻子组件共享，并且共同父组件天然拥有这项业务：

```text
SearchPage
├── SearchForm
└── SearchResult
```

搜索条件可以放在 `SearchPage`，通过 props 与 emits 连接两个子组件，不必立即建立全局 store。

### 3.3 Pinia 全局状态

跨布局、跨页面或多个不相邻组件共享，而且生命周期通常与应用或登录会话一致：

- 当前用户和登录凭证；
- 主题、语言、侧边栏折叠偏好；
- 后台菜单与权限节点；
- 多标签页导航状态。

简单判断方法：先问“谁需要它”，再问“需要活多久”。全局 store 不是 `ref()` 的替代品，而是共享状态的归属地。

## 4. Pinia 如何接入 Vue 应用

安装 Pinia 后，在应用入口创建唯一的 Pinia 实例并注册：

```ts
// src/main.ts
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

const app = createApp(App)
const pinia = createPinia()

app.use(pinia)
app.mount('#app')
```

`createPinia()` 创建 store 的运行容器。`app.use(pinia)` 把它安装到当前 Vue 应用，使组件中的 store 能找到活动的 Pinia 实例。

通常一个 Vue 应用只创建一个 Pinia 实例。BuildAdmin 把创建逻辑单独放在 `src/stores/index.ts`，再由 `main.ts` 导入，这是较大项目中常见的组织方式。

## 5. 定义 Store 的两种写法

Pinia 支持选项式和组合式两种写法。它们能力相近，只是组织方式不同。

### 5.1 选项式 Store

```ts
import { defineStore } from 'pinia'

export const useCounterStore = defineStore('counter', {
  state: () => ({
    count: 0,
  }),
  getters: {
    doubleCount: (state) => state.count * 2,
  },
  actions: {
    increment() {
      this.count++
    },
  },
})
```

它与 Vue 的 Options API 类似：`state`、`getters`、`actions` 分区明显。

### 5.2 组合式 Store

```ts
import { computed, ref } from 'vue'
import { defineStore } from 'pinia'

export const useCounterStore = defineStore('counter', () => {
  const count = ref(0)
  const doubleCount = computed(() => count.value * 2)

  function increment() {
    count.value++
  }

  return { count, doubleCount, increment }
})
```

在组合式 store 中：

- `ref()`、`reactive()` 对应 state；
- `computed()` 对应 getters；
- 普通函数对应 actions；
- 需要供组件使用的内容必须返回。

本节实践采用组合式写法，因为它与已经学习的 Composition API 直接对应。阅读 BuildAdmin 时两种写法都会遇到：`adminInfo.ts` 使用选项式，`config.ts` 使用组合式。

## 6. state、getters、actions 的职责

### 6.1 state 是源数据

用户信息的源数据可以是：

```ts
const id = ref(0)
const username = ref('')
const nickname = ref('')
const token = ref('')
```

不要把可以从现有状态直接算出的数据重复保存。例如已有 `nickname` 和 `username`，显示名称应当计算，而不是再维护一个容易不同步的 `displayName` state。

### 6.2 getter 是派生数据

```ts
const displayName = computed(() => nickname.value || username.value || '未登录')
```

当昵称存在时显示昵称，否则降级到用户名，再否则显示“未登录”。它没有独立来源，因此用 computed/getter 最合适。

getter 应尽量保持纯粹：读取现有 state 并返回结果，不在计算过程中修改其他状态或发请求。

### 6.3 action 是业务动作

```ts
function updateNickname(value: string) {
  nickname.value = value.trim()
}
```

组件当然可以直接写 `userStore.nickname = value`，Pinia 允许这样做。但当修改包含校验、多字段联动、异步请求或清理规则时，action 能把业务含义集中起来：

```ts
function clearUser() {
  id.value = 0
  username.value = ''
  nickname.value = ''
  token.value = ''
}
```

组件只需表达“清空当前用户”，不必知道需要清空哪些字段。

action 可以是异步函数：

```ts
async function loadProfile() {
  const profile = await requestProfile()
  id.value = profile.id
  username.value = profile.username
  nickname.value = profile.nickname
}
```

Pinia 不要求像某些旧式状态库那样额外定义 mutation；action 可以直接修改 state。

## 7. 完整用户 Store 示例

```ts
// src/stores/user.ts
import { computed, ref } from 'vue'
import { defineStore } from 'pinia'

export interface UserProfile {
  id: number
  username: string
  nickname: string
  token: string
}

const emptyUser: UserProfile = {
  id: 0,
  username: '',
  nickname: '',
  token: '',
}

export const useUserStore = defineStore('user', () => {
  const id = ref(emptyUser.id)
  const username = ref(emptyUser.username)
  const nickname = ref(emptyUser.nickname)
  const token = ref(emptyUser.token)

  const displayName = computed(
    () => nickname.value || username.value || '未登录',
  )
  const isLoggedIn = computed(() => token.value !== '')

  function setUser(profile: UserProfile) {
    id.value = profile.id
    username.value = profile.username
    nickname.value = profile.nickname
    token.value = profile.token
  }

  function updateNickname(value: string) {
    nickname.value = value.trim()
  }

  function clearUser() {
    id.value = emptyUser.id
    username.value = emptyUser.username
    nickname.value = emptyUser.nickname
    token.value = emptyUser.token
  }

  return {
    id,
    username,
    nickname,
    token,
    displayName,
    isLoggedIn,
    setUser,
    updateNickname,
    clearUser,
  }
})
```

注意 `emptyUser` 只是初始值模板。`clearUser()` 对各字段赋值，而不是让多个 store 实例共享一个可修改对象。

## 8. 在组件中使用 Store

### 8.1 直接使用 store 对象

```vue
<script setup lang="ts">
import { useUserStore } from '@/stores/user'

const userStore = useUserStore()

function mockLogin() {
  userStore.setUser({
    id: 8,
    username: 'hunter',
    nickname: 'Hunter',
    token: 'demo-token',
  })
}
</script>

<template>
  <p>你好，{{ userStore.displayName }}</p>
  <button @click="mockLogin">模拟登录</button>
</template>
```

模板会自动解包 store 中的 ref，因此写 `userStore.displayName`，不需要 `.value`。

### 8.2 为什么不能随意解构 Store

下面的写法可能破坏状态属性与 store 的响应式连接：

```ts
const userStore = useUserStore()
const { nickname, displayName } = userStore
```

普通 JavaScript 解构会取出当前属性值。要把 state 和 getters 解构成仍有响应性的 ref，应使用：

```ts
import { storeToRefs } from 'pinia'

const userStore = useUserStore()
const { nickname, displayName } = storeToRefs(userStore)
const { updateNickname } = userStore
```

为什么 action 可以直接解构？action 是绑定到 store 的方法，不需要用 `storeToRefs()` 包装。一个实用规则是：

- state 和 getters：通过 `storeToRefs(store)` 解构；
- actions：直接从 store 解构，或继续用 `store.action()` 调用。

## 9. 完整应用配置 Store 示例

```ts
// src/stores/app.ts
import { computed, ref } from 'vue'
import { defineStore } from 'pinia'

export const useAppStore = defineStore('app', () => {
  const sidebarCollapsed = ref(false)

  const sidebarWidth = computed(() =>
    sidebarCollapsed.value ? '64px' : '220px',
  )
  const sidebarActionText = computed(() =>
    sidebarCollapsed.value ? '展开侧边栏' : '折叠侧边栏',
  )

  function toggleSidebar() {
    sidebarCollapsed.value = !sidebarCollapsed.value
  }

  function setSidebarCollapsed(value: boolean) {
    sidebarCollapsed.value = value
  }

  return {
    sidebarCollapsed,
    sidebarWidth,
    sidebarActionText,
    toggleSidebar,
    setSidebarCollapsed,
  }
})
```

这里保存的源数据只有布尔值。宽度和按钮文字都能由它计算，因此作为 getters，而不是三份需要手动保持一致的 state。

布局组件可以这样使用：

```vue
<script setup lang="ts">
import { storeToRefs } from 'pinia'
import { useAppStore } from '@/stores/app'
import { useUserStore } from '@/stores/user'

const appStore = useAppStore()
const userStore = useUserStore()
const { sidebarWidth, sidebarActionText } = storeToRefs(appStore)
const { displayName } = storeToRefs(userStore)
</script>

<template>
  <header>
    <button @click="appStore.toggleSidebar">
      {{ sidebarActionText }}
    </button>
    <span>{{ displayName }}</span>
  </header>
  <aside :style="{ width: sidebarWidth }">
    菜单
  </aside>
</template>
```

## 10. 多组件共享时的运行过程

假设 `AdminLayout.vue` 和 `HomeView.vue` 都调用 `useUserStore()`：

1. 应用安装 Pinia。
2. 布局首次调用 `useUserStore()`，Pinia 创建 id 为 `user` 的 store。
3. 首页再调用 `useUserStore()`，Pinia 返回已经存在的同一 store，而不是创建一份新用户数据。
4. 首页调用 `updateNickname('新昵称')`。
5. action 修改 store 中的 `nickname`。
6. `displayName` getter 重新计算。
7. 布局与首页中使用 `displayName` 的模板同时更新。

这就是跨组件联动的核心。它不是两个变量互相通知，而是两个组件共同订阅一份响应式状态。

## 11. 更新 State 的常用方式

### 11.1 直接修改

```ts
userStore.nickname = '新的昵称'
```

适合简单、明确的单字段更新，但业务规则容易散落在组件中。

### 11.2 调用 action

```ts
userStore.updateNickname('新的昵称')
```

业务含义清楚，便于加入校验和复用，是本节实践优先采用的方式。

### 11.3 `$patch()` 批量更新

```ts
userStore.$patch({
  username: 'hunter',
  nickname: 'Hunter',
})
```

适合一次更新多个字段。BuildAdmin 的 `adminInfo.dataFill()` 就使用 `$patch()` 批量填充管理员状态。

### 11.4 `$reset()` 的边界

选项式 store 原生支持 `$reset()` 恢复 `state()` 返回的初始状态。组合式 store 需要自己编写清理 action，例如前文的 `clearUser()`。这样也能明确控制哪些字段被清理。

## 12. 内存状态与持久化

Pinia 默认状态存在当前网页的 JavaScript 内存中。刷新页面意味着旧页面运行环境被销毁，应用重新执行，store 回到初始值。

持久化通常按以下过程工作：

```text
store 更新
→ 序列化部分状态
→ 写入 localStorage/sessionStorage
→ 页面刷新
→ 新 store 创建
→ 从存储中恢复状态
```

Pinia 本身不自动把所有状态写入浏览器存储。项目可以手写同步逻辑，也可以安装持久化插件。BuildAdmin 使用 `pinia-plugin-persistedstate`：

```ts
const pinia = createPinia()
pinia.use(piniaPluginPersistedstate)
```

然后在具体 store 中配置 `persist`。这说明“使用 Pinia”和“启用持久化”是两件不同的事。

### 12.1 不要盲目持久化全部状态

适合持久化的例子：

- 主题和语言偏好；
- 侧边栏折叠偏好；
- 在安全方案允许下保存的登录会话信息。

通常不需要持久化的例子：

- 正在加载的 loading；
- 当前打开的临时弹窗；
- 只在本页有效的表单校验错误；
- 可以轻易重新请求且可能已经过期的大量业务数据。

特别注意：持久化插件提供的是数据保存能力，不自动解决安全问题。`localStorage` 中的数据可被页面 JavaScript 读取；token 如何保存需要结合 XSS 防护、后端会话方案和项目威胁模型决定。

## 13. BuildAdmin 源码拆解

### 13.1 Pinia 入口

文件：`buildadmin/web/src/stores/index.ts`

```ts
import { createPinia } from 'pinia'
import piniaPluginPersistedstate from 'pinia-plugin-persistedstate'

const pinia = createPinia()
pinia.use(piniaPluginPersistedstate)

export default pinia
```

文件：`buildadmin/web/src/main.ts`

```ts
const app = createApp(App)
app.use(pinia)
```

职责分工很清楚：stores 入口负责创建和配置 Pinia，应用入口只负责安装。

### 13.2 `adminInfo`：当前管理员状态

它保存 id、用户名、昵称、头像、token、refresh token、是否超级管理员等数据。主要 actions 包括：

- `dataFill()`：批量填充资料，可选择排除 token；
- `removeToken()`：清除两类 token；
- `setToken()` 和 `getToken()`：集中处理认证 token；
- `setSuper()`：修改超级管理员标记。

这类数据会被顶部栏、登录逻辑、请求层和权限判断共同使用，明显属于全局状态。

### 13.3 `config`：应用显示与行为偏好

它保存布局模式、暗色状态、菜单宽度、菜单折叠、语言和 CRUD 同步偏好。`menuWidth()` 根据折叠状态返回宽度，作用相当于 getter。`setLayout()`、`setLang()` 等函数是 actions。

它使用组合式 store，说明组合式写法同样可以承载大型真实配置。

### 13.4 `siteConfig`：服务端下发的站点配置

它保存站点名、版本、CDN/API 地址、上传方式、头部导航以及初始化标记。`dataFill()` 用服务端返回值填充 store，`setInitialize()` 则记录初始化是否完成。

初始化标记很重要：它不只是显示数据，还协调应用启动时序，避免相同配置重复请求或业务在配置未准备好时过早执行。

### 13.5 为什么拆成多个 Store

如果把管理员、主题、菜单、站点配置和标签页全塞入一个 `globalStore`，它会越来越难读，任何组件都可能修改任何字段。BuildAdmin 按业务职责拆分，让每个 store 有清楚的变化原因：

- 管理员身份变化 → `adminInfo`；
- 布局偏好变化 → `config`；
- 站点初始化数据变化 → `siteConfig`；
- 标签页变化 → `navTabs`。

拆分的依据不是“一个页面一个 store”，而是相互内聚的业务状态与动作。

## 14. 常见错误

### 错误一：在安装 Pinia 前使用 Store

组件外部模块如果在 `app.use(pinia)` 之前直接调用 `useUserStore()`，可能出现没有活动 Pinia 的错误。组件的 `setup` 通常发生在插件安装之后，不会有此问题；路由工具等组件外代码需要注意初始化顺序，必要时显式传入 Pinia 实例。

### 错误二：普通解构破坏响应性

```ts
const { nickname } = useUserStore()
```

要解构响应式状态，应使用 `storeToRefs()`；或者不解构，始终通过 `userStore.nickname` 访问。

### 错误三：把所有 `ref()` 都搬进 Store

全局化会扩大状态生命周期和可修改范围，使简单组件反而更难理解。状态只属于一个组件时，继续放在组件内。

### 错误四：重复保存派生值

同时保存 `sidebarCollapsed`、`sidebarWidth`、`buttonText`，每次修改要同步三项，容易出现矛盾。只保存折叠布尔值，其他内容用 getters 计算。

### 错误五：action 只做无意义的一层包装

并非任何单字段赋值都必须有 action。action 的价值在于表达业务语义、集中校验、多字段联动和异步流程。本课程要求关键修改使用 action，是为了练习清晰的业务边界，而不是规定所有项目只能这样写。

### 错误六：以为刷新后状态天然存在

Pinia 默认只管理内存中的响应式状态。需要刷新恢复时，还要设计持久化范围和恢复时机。

### 错误七：把持久化当成安全认证

浏览器保存了一个 token，不代表 token 有效，也不代表用户有权限。后端仍必须校验 token、有效期和权限。

8. BuildAdmin 的 `adminInfo` 和 `config` 为什么不合并为一个 store？
9. 侧边栏宽度应该保存为 state，还是根据折叠状态计算？为什么？

## 16. 参考答案

1. 它只有一个组件需要，生命周期也与弹窗一致；放在组件内更直接，没必要扩大为全局状态。
2. state 是事实来源；getter 是根据 state 计算出的派生结果，不应维护一份重复来源。
3. 都可以。action 可以是同步或异步函数，也可以直接修改 store state。
4. Pinia 根据唯一 store id 缓存仓库；同一 Pinia 实例下再次调用会取得同一个响应式 store。
5. 普通解构会失去与响应式对象属性的连接；`storeToRefs()` 把 state/getters 转成保持连接的 ref。action 是绑定方法，可以直接解构。
6. 页面运行环境重建，store 重新执行初始值，默认状态会丢失。
7. 它把指定状态保存到浏览器存储并在重建时恢复；它不防止 XSS，不验证 token，也不代替后端权限校验。
8. 两者变化原因和业务职责不同。拆开能保持内聚、降低耦合，也让组件只依赖需要的仓库。
9. 通常只保存折叠布尔值，宽度用 getter 计算，避免两份状态不同步。
10. `ref/reactive` 对应 state，`computed` 对应 getters，返回的普通函数对应 actions。
