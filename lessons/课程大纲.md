# BuildAdmin 前端 30 天课程大纲

## 一、课程定位

| 项目 | 内容 |
| --- | --- |
| 学习周期 | 30 天，每天 1 节，共 30 节 |
| 建议投入 | 每天 2～3 小时：学习 40 分钟、读源码 40 分钟、动手 60～100 分钟、复盘 10 分钟 |
| 学习对象 | 有少量 HTML、CSS、JavaScript 基础的前端初学者 |
| 源码目录 | `E:\Project\FrontEnd\buildadmin\web` |
| 练习目录 | `E:\Project\MyProject\ba-learn` |
| 最终成果 | 独立复刻一个具备登录、布局、权限路由、CRUD、主题切换和数据看板的后台管理系统 |
| 技术主线 | Vue 3、TypeScript、Vite、Vue Router、Pinia、Axios、Element Plus、ECharts |

本课程不是一次性知识清单，而是一门由 Coach 按学习进度逐日推进的源码学习课。每节课只围绕一个可验收主题展开，通过“完整教材 → 诊断与讲解 → 源码拆解 → 动手实践 → 理解检查 → 验收归档”形成学习闭环，最终让学生能够脱离教程复刻类似的后台管理系统。

## 二、培养目标与结课能力

完成课程后，学生应当能够：

1. 用自己的话说明 BuildAdmin 前端从启动、登录到呈现后台页面的完整流程。
2. 看懂 Vue 单文件组件、Composition API 和常用 TypeScript 类型。
3. 独立搭建后台布局、路由、状态管理、请求层和登录鉴权。
4. 独立完成一个列表查询、新增、编辑、删除、分页和表单校验的 CRUD 模块。
5. 理解 BuildAdmin 的动态菜单、标签页、权限控制和通用表格设计，而不是机械复制源码。
6. 完成一个可运行、可构建、结构清晰的复刻项目，并能讲清关键设计取舍。

课程不以“照着源码写出相同代码”为目标。学生需要逐步形成三种能力：

1. **源码阅读能力**：知道从哪里进入、沿什么调用关系追踪，以及如何区分核心骨架和产品细节。
2. **独立实现能力**：能先说清数据流和职责边界，再在练习项目的指定文件中实现功能。
3. **迁移复刻能力**：能解释自己的实现与 BuildAdmin 源码的相同点、差异和取舍，而不是机械复制。

## 三、课程阶段与递进逻辑

| 阶段 | 天数 | 阶段目标 | 阶段作品 |
| --- | --- | --- | --- |
| 第一阶段：建立地图 | 第 1～3 天 | 会运行、会定位、看懂项目入口与模块关系 | 能运行项目并追踪启动链路 |
| 第二阶段：Vue 与 TS 地基 | 第 4～8 天 | 掌握读写 BuildAdmin 页面必需的 Vue 3、TS、样式基础 | 登录页静态原型和可复用组件 |
| 第三阶段：后台骨架 | 第 9～14 天 | 完成路由、状态、布局、菜单、标签页和主题 | 可导航的后台壳子 |
| 第四阶段：数据与登录 | 第 15～18 天 | 完成请求封装、登录态、守卫和错误处理 | 可模拟登录的后台系统 |
| 第五阶段：CRUD 核心 | 第 19～24 天 | 理解并复刻表格、搜索、表单和权限按钮 | 完整的用户管理模块 |
| 第六阶段：产品化与结课 | 第 25～30 天 | 完成看板、配置、质量检查、综合复刻与答辩 | 可演示的后台管理系统 |

阶段之间遵循以下递进关系：先建立项目地图，再补齐阅读源码所需的 Vue 与 TypeScript 基础；随后搭建后台骨架，接通登录和数据链路；在此基础上完成 CRUD 与权限，最后进行产品化整合。若某节核心目标没有通过，应先补强该知识点，再进入依赖它的后续课程，但每日课程的节次和主题不变。

| 第 21 节 | 搜索排序与重置 | 查询模型、条件组合、排序、防抖、重置 | 用户搜索区 | 搜索条件与请求参数一致，可一键恢复默认状态 |

## 五、复刻项目的最小功能范围

结课作品暂定为“轻量用户运营后台”，必须包含：

1. 登录与退出。
2. 后台基础布局、折叠菜单、面包屑或标签页。
3. 首页指标卡与图表。
4. 用户管理 CRUD、搜索、分页和批量删除。
5. 角色切换、动态菜单和按钮级权限。
6. 明暗主题切换，设置能够持久化。
7. 统一请求封装、Loading、成功提示和错误提示。
8. TypeScript 类型检查与生产构建通过。

不把真实后端开发列为本期硬性目标。前期使用本地模拟数据，把精力集中在前端架构；如已有可用接口，可在第 29 节替换模拟 API。

## 六、每节课的教学闭环

每节课按以下顺序逐步开展，不一次性把所有任务倾倒给学生：

1. **读取进度**：读取 `学习进度.md`、本大纲和上一节课程记录，确认当前节次、已掌握内容和待补问题。
2. **创建课程文件**：在 `lessons` 下创建 `第xx节-课程名` 目录，并按统一格式建立课程记录；非纯练习课同时建立独立学习资料。
3. **开课诊断**：用少量问题了解学生当前理解。诊断用于调整讲解起点，不作为惩罚性考试。
4. **分段教学**：一次讲清一个小知识点，随即通过追问、代码阅读或小任务检查理解，再决定是否继续。
5. **源码拆解**：定位 BuildAdmin 的相关入口、关键文件、调用关系和数据流，用初学者能理解的语言解释“它解决什么问题、数据从哪里来、经过哪里、最后影响什么”。
6. **指定实践**：需要写代码时，明确给出练习目录、文件名、目标和完成标志；学生完成后通知 Coach 检查。
7. **反馈修正**：Coach 先判断本节核心知识是否成立，再指出真正影响理解或运行的问题；非关键的风格问题不得喧宾夺主。
8. **理解检查**：围绕本节知识让学生解释、判断、排错或实现。学生可以用自然语言、代码或自己习惯的方式回答。
9. **工程验证**：Coach 根据风险执行类型检查、构建和必要的运行验证，并把结果与错误原因记录下来。
10. **结课归档**：记录掌握情况、遗留疑问和下一步，更新 `学习进度.md`；未通过核心验收时标记为待补强。

## 七、统一课程文件规范

### 7.1 目录与文件命名

每节课使用固定目录：

```text
lessons/
└── 第xx节-课程名/
    ├── 第xx节-课程名.md
    └── 第xx节-学习资料.md
```

- `第xx节-课程名.md` 是互动课程记录，保存实际发生的教学全过程。
- `第xx节-学习资料.md` 是独立教材。若该节目标只是运用已经学过的知识完成练习，可以省略学习资料，但必须保留课程记录。
- 节次统一使用两位数字，例如 `第08节`、`第14节`。

### 7.2 互动课程记录固定结构

所有 `第xx节-课程名.md` 统一使用以下一级结构，不得随课程任意更换格式：

1. 课程信息
2. 本节目标
3. 开课诊断
4. 学习路线
5. 教学与互动记录
6. 动手任务
7. 本节理解检查
8. 验收结果
9. 学习小结
10. 进度更新

其中“教学与互动记录”必须按照真实发生顺序持续追加。学生的知识性提问保留原文，Coach 的实质回答保留完整内容、代码和推导过程，不得只写结论摘要。学生只是询问题意、任务范围或操作口令时，可以不逐字归档。

### 7.3 学习资料固定结构

所有 `第xx节-学习资料.md` 统一使用以下一级结构：

1. 学习目标
2. 前置知识
3. 核心概念
4. BuildAdmin 源码拆解
5. 完整示例与运行过程
6. 常见错误
7. 自测题
8. 参考答案

教材必须能够脱离对话独立阅读和复习：

- 语言或框架知识要补齐理解该主题所需的前置解释，并提供输入端、处理端、输出端的完整代码或等价的完整链路。
- 完整示例不仅展示最终代码，还要解释代码怎样启动、数据怎样变化、页面或控制台会出现什么结果。
- 项目相关内容要指出准确的源码文件，先用通俗语言说明职责，再拆解关键代码和调用过程。
- 只讲本节必需内容；超出初学者当前阶段的语法要先拆开解释，拓展内容与核心要求明确区分。
- 自测题只检查知识理解，参考答案应说明原因，不能只给“对/错”或最终代码。

## 八、输出与验收原则

1. 输出的目的，是判断学生是否真正理解本节核心知识，而不是检查表达形式。
2. 不得要求“不少于多少字”，不得强制学生使用表格、Mermaid、报告、固定话术或其他指定形式作答。
3. 学生可使用自然语言、代码片段、运行现象或自己的例子回答；只要足以证明理解，就应视为有效输出。
4. Coach 可以在教材和讲解中使用表格、流程图、Mermaid 或对比清单帮助理解，但不能把这些形式反过来强加给学生。
5. 验收优先关注：概念是否理解、数据流是否说得通、代码能否实现目标、遇到问题能否定位原因，以及能否解释与 BuildAdmin 源码的对应关系。
6. 对学生代码的反馈先抓本节重点。命名偏好、排版和非关键抽象不应阻挡通过；会导致错误理解、功能失效或后续无法扩展的问题必须说明并修正。

## 九、课程推进与进度管理

1. 当学生发送“开始今天的课程”时，Coach 必须先读取 `lessons/学习进度.md` 和 `lessons/课程大纲.md`，再从记录中的下一节开始。
2. 课程采用 Study Mode：通过讲解、追问、提示、实践和反馈带领学生逐步得出答案，不替学生包办核心练习。
3. 每次只推进当前一节，不提前灌输整门课程；学生临时提出的知识问题在当前对话回答，并按规则归档。
4. 涉及编码时必须明确目录和文件名。学生完成后由 Coach 检查实际文件并反馈，不让学生自行猜测验收范围。
5. 类型检查、生产构建、重复调用、异常路径等机械性验证默认由 Coach 执行，学生主要承担能促进理解的关键实现与排错。
6. 每节结束后更新 `学习进度.md`，记录状态、实际产物、掌握内容、待补问题和下一节；不得提前把未完成课程标记为完成。
7. 若核心目标未通过，保持原节次并安排补强；每日课程安排、30 天编号和课程主题不因补强而改动，可缩减非必要拓展内容。
8. 已发生的课程记录只追加或纠正事实，不虚构学生回答，也不为了格式整齐删除有复习价值的历史问答。
