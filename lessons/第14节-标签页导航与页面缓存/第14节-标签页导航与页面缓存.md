它能让我们显示两个标签，点击“用户详情”时执行：

```ts

```

但备注存在于用户详情组件内部：

```vue
<script setup lang="ts">

</script>

<template>
  <input v-model="note" />
</template>
```

输入“待联系”后，组件里的 `note` 变成了 `'待联系'`，上面的标签数组没有变化。

在没有缓存、也没有另外保存备注的情况下，从用户详情切到首页，再回来，会经历：

```text
打开用户详情 → 创建组件，note 初始为 ''
输入备注     → note 变成 '待联系'
切到首页     → 用户详情组件卸载，局部状态随之丢失
点击详情标签 → 根据地址重新创建组件，note 又从 '' 开始
```

这里的“组件实例”，就是组件实际运行起来的那一份，里面有它自己的 `note` 等状态。

今天要学的 `KeepAlive`，就是让切走的页面实例暂时保留下来，再回来时继续使用，因此可以保留里面的备注。具体代码稍后再讲。

你先判断一个现象：**切回用户详情后，顶部标签还在，但备注变空了。这说明“标签列表没记住”，还是“页面里的状态没保住”？**

学生原问题：

> 这跟顶部标签有什么关系呢？不就是组件实例销毁里面的所有内容都销毁了吗

Coach 完整回答：

对，你这个判断完全正确：**备注变空的直接原因，就是用户详情组件实例被销毁了。它和顶部标签本身没有直接关系。**

顶部标签只是一个导航入口。它最多记住：

```ts
{
  title: '用户详情',
  fullPath: '/admin/users/8'
}
```

点击它，相当于再次执行：

```ts
router.push('/admin/users/8')
```

它不会自动保存 `note`，也不会自动阻止组件销毁。所以可以出现：

```text
标签还在
≠ 页面实例还在
≠ 页面中的输入还在
```

这两个功能放在同一节课，是因为后台产品通常把它们设计成一个联动体验：

1. 用户打开页面，标签栏增加一个入口。
2. 用户切换标签，本质上是切换路由。
3. 路由切走时，KeepAlive 决定页面实例是否保留。
4. 用户关闭标签，业务通常还希望同时释放这个页面的缓存。

因此它们的职责依然分开：

```text
顶部标签：管理打开过哪些页面，以及切换、关闭入口
KeepAlive：管理切走后的组件实例是否继续存在
```

如果项目不需要保留表单、滚动位置等页面状态，完全可以只做顶部标签而不用 KeepAlive；点击旧标签时重新创建页面即可。反过来，没有顶部标签也能使用 KeepAlive，例如在两个普通导航链接之间切换时缓存页面。

本节把两者放在一起，是为了实现常见后台行为，而不是因为顶部标签负责保存组件内容。

学生已经准确指出“组件实例销毁导致局部内容销毁”，因此标签记录与页面实例的职责区别已通过，不再重复追问。

比如原来数据库里的备注是“明天回访”：

```text
打开详情 → 请求后端 → 输入框显示“明天回访”

```

这几件事解决的是不同问题：

| 机制 | 保存什么 |
| --- | --- |
| 提交到后端 | 已确认保存的业务数据 |
| KeepAlive | 页面实例中的临时状态，例如未提交的输入、局部筛选条件 |
| 标签列表 | 打开过的页面入口 |

**缓存不是表单必须具备的功能，更不能代替提交保存。** 如果产品允许切走后丢弃未保存内容，重新进入时请求后端就可以；也可以在离开前提醒用户保存。若希望用户切到别页查资料，再回来接着编辑，缓存才有用。

### 编码途中提问：storeToRefs 为什么不能解构 action

学生原问题（保留粘贴时的转义字符）：

> const *{addTab}&#x20;*= *storeToRefs*(navTabs)Vue: Property addTab does not exist on type
> ToRefs\<Pick<{
> &#x20;   tabs: Ref\<NavTab[], NavTab[]>;
> &#x20;   addTab: (tab: NavTab) => void;
> }, "tabs">> & ToRefs\<PiniaCustomStateProperties<{
> &#x20;   tabs: NavTab[];
> }>> & \_ToComputedRefs<...>解构报错是为什么

Coach 已核对 AdminTabs.vue 中确实存在 const {addTab} = storeToRefs(navTabs)，并核对 Pinia 官方文档。未替学生修改代码，任务三仍在进行。

Coach 完整回答：

因为 **`storeToRefs()` 会跳过 action，而你的 `addTab` 正是一个 action。**

你在 store 中返回的两个东西，职责不同：

```ts
return {
  tabs,   // 状态：响应式数据
  addTab, // action：操作数据的函数
}
```

所以正确的解构方式是：

```ts
const navTabs = useNavTabsStore()

const { tabs } = storeToRefs(navTabs) // 状态通过 storeToRefs 提取
const { addTab } = navTabs           // action 直接从 store 解构
```

使用时也不同：

```ts
console.log(tabs.value) // 解构得到的状态是 ref，脚本中用 .value

addTab({
  title: '用户详情',
  fullPath: '/admin/users/8',
  fixed: false,
}) // action 仍然是函数，直接调用
```

为什么状态需要这样处理？因为我们希望取出来的 `tabs` 始终关联 store 中的状态，即使以后整个数组被替换，也能读到新数组。函数则不需要转换成 ref，Pinia 支持直接解构 action。[Pinia 官方说明](https://pinia.vuejs.org/core-concepts/#destructuring-from-a-store)

你那段很长的报错，核心是：

```text
storeToRefs(navTabs) 的结果里只有 tabs，没有 addTab。
因此不能从这个结果中解构 addTab。
```

**当前只需要把这行改为：**

```ts
const { addTab } = navTabs
```

也可以不解构，继续用 `navTabs.addTab(...)`。两种写法都可以，改好后继续补完 watch 回调即可。
